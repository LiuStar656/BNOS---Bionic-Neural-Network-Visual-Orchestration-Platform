# 15 复合节点配置文件与资源组

## 概述

为复合节点建立正式的配置文件体系与目录资源组。核心是 `composite.json` Schema 定义，替代此前散落在代码中的临时路径拼接。同时引入配置文件自愈能力 — 损坏时从 `node_clusters.json` 自动重建，以及 `.archive` 历史日志归档机制。

## 二、关键设计

### 2.1 composite.json Schema

```json
{
  "composite_id": "comp_abc123",
  "display_name": "图像处理流水线",
  "dag": {
    "nodes": { "<node_id>": { "type": "...", "config": {...} } },
    "edges": [ { "from": "<node_id>.<port>", "to": "<node_id>.<port>" } ]
  },
  "ports": {
    "inputs":  [ { "key": "image",   "label": "输入图像", "type": "image" } ],
    "outputs": [ { "key": "result",  "label": "处理结果", "type": "image" } ]
  },
  "resource_budget": {
    "cpu_cores": 4,
    "memory_mb":  2048
  },
  "structure_fingerprint": "a1b2c3d4e5f6",
  "created_at": "2026-07-12T10:30:00",
  "updated_at": "2026-07-12T11:00:00"
}
```

Schema 承载了复合节点的**完整身份**（id + display_name）、**DAG 拓扑**（nodes + edges）、**对外暴露端口**（inputs/outputs）以及**资源预算**，使得 `composite.json` 成为复合节点的唯一真实源（single source of truth）。

### 2.2 node_registry.json 设计

```json
{
  "composite_id": "comp_abc123",
  "children": {
    "node_1": { "status": "running", "pid": 12345, "output_path": "..." },
    "node_2": { "status": "running", "pid": 12346, "output_path": "..." },
    "node_3": { "status": "done",    "pid": null,  "output_path": "..." }
  }
}
```

登记簿记录每个子节点的**运行时状态**，与 `composite.json` 中静态 DAG 描述分离。运行时信息（PID、状态、输出路径）属于热数据，不应混入冷配置。

### 2.3 配置损坏自愈

```
_load_composite_config()
    │
    ├── 解析成功 → 返回
    │
    └── 解析失败 (JSONDecodeError / KeyError)
            │
            ├── 日志警告 "composite.json corrupted, rebuilding..."
            │
            └── _rebuild_composite_config()
                    │
                    ├── 从 node_clusters.json 提取该复合节点的子节点列表
                    ├── 生成最小可用 composite.json（含 DAG 和端口）
                    ├── 指纹标记为 "rebuilt"
                    └── 返回恢复后的配置
```

损坏恢复路径保证复合节点不会因为一个配置文件损坏而彻底不可用。最小可用版本可能丢失一些元数据（如 resource_budget 自定义值），但所有核心功能（DAG 执行、端口映射）均可恢复。

### 2.4 归档策略

```
archive 命名规则:
  composite_nodes/.archive/<comp_id>_<structure_fingerprint>_<timestamp>/

裁剪策略 (_prune_archives):
  - 每个 comp_id 最多保留 10 个归档版本
  - 超出部分按时间升序删除（保留最新 10 个）
  - 在每次 _decompress_cleanup 后触发
```

结构指纹确保同一 DAG/端口结构的不同版本可区分；时间戳提供版本回溯能力；10 上限防止磁盘无限增长。

## 三、文件树

### 复合节点运行时目录

```
composite_nodes/<comp_id>/
├── composite.json              # 身份 + DAG + 端口 + 资源预算（Schema 定义见 2.1）
├── node_registry.json          # 子节点运行时状态登记簿
├── logs/                       # 复合节点日志
│   ├── composite_output.log    # 编排器 stdout
│   └── composite_error.log     # 编排器 stderr
├── orchestrator.py             # 编排器脚本
└── venv/                       # 合并虚拟环境
```

### 归档目录

```
composite_nodes/.archive/
├── comp_abc123_a1b2c3d4e5f6_20260712T103000/
│   ├── composite.json          # 结构快照
│   ├── composite_output.log    # 历史日志
│   └── composite_error.log
├── comp_abc123_d4e5f6a1b2c3_20260712T110000/
│   └── ...
└── comp_xyz789_.../
    └── ...
```

## 四、行为变化

### 4.1 Compress（折叠为复合节点）

```
旧行为: 仅将子节点数据写入 node_clusters.json，无独立配置文件

新行为:
  1. _create_comp_config_dir(comp_id)     → 创建 composite_nodes/<id>/ 及 logs/
  2. _write_composite_config(comp_id)      → 写入 composite.json
  3. _write_node_registry(comp_id)         → 写入 node_registry.json
  4. 日志输出重定向至 composite_nodes/<id>/logs/
```

### 4.2 启动时自动迁移

```
_startup_check → _migrate_existing_composites()
    │
    └── 遍历 node_clusters.json 中所有复合节点
            │
            └── 若 composite_nodes/<id>/composite.json 不存在
                    │
                    └── 从 node_clusters.json 提取数据 → 补建配置文件
```

**背景**：在此改动之前创建的复合节点没有配置文件。启动时自动扫描并补建，保证存量项目无缝升级。

### 4.3 Decompress（解压/还原为普通节点）

```
旧行为: 直接还原子节点，旧日志保留在 venv/logs（混乱）

新行为:
  1. _decompress_cleanup(comp_id)
       ├── 创建 .archive/<comp_id>_<fingerprint>_<timestamp>/
       ├── 复制 composite.json → archive（结构快照）
       ├── 移动 logs/*.log → archive（历史日志）
       └── 删除 composite_nodes/<comp_id>/ 全部内容
  2. _prune_archives() → 裁剪至 10 个归档版本
  3. 还原子节点至画布
```

### 4.4 日志路径迁移

```
旧路径: venv/logs/composite_output.log  (依赖 display_name，不稳定)

新路径: composite_nodes/<comp_id>/logs/composite_output.log
                                              /composite_error.log
```

路径与 `display_name` 解耦，仅依赖不变的 `comp_id`。`node_list_ops.py` 的 `_get_log_files` 同步修正。

### 4.5 配置损坏恢复

```
触发条件: composite.json 内容损坏（JSON 解析失败或关键字段缺失）

恢复流程:
  1. 日志记录警告 + 损坏原因
  2. 调用 _rebuild_composite_config(comp_id)
  3. 从 node_clusters.json 提取该复合节点的子节点拓扑
  4. 生成最小可用 composite.json 覆盖写回
  5. structure_fingerprint 标记为 "rebuilt"
  6. 用户无感知继续使用（可能丢失自定义 resource_budget）
```
