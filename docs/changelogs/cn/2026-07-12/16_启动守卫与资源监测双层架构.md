# 16 启动守卫与资源监测双层架构

## 概述

引入两项相互关联的安全与可见性机制：(1) **启动守卫**，双向互斥地阻止独立节点与复合节点之间的启动冲突；(2) **资源监测双层架构**，将复合节点的编排器进程作为独立监控实体，子节点以缩进子行形式展示。

二者协同：启动守卫从源头防止冲突状态产生，双层架构让运行中的父子进程关系一目了然。

## 二、关键设计

### 2.1 启动守卫 — 双向互斥

启动守卫解决一个根本性冲突：**同一个复合节点内的子节点，既能以独立模式运行，也能被复合节点编排器管理**。若两种模式同时存在，将导致资源争抢、数据竞态和预期外的行为。

```
场景 A: 用户启动独立节点
  start_selected_node_by_name()
      │
      └── check_subnode_start(node_name)
              │
              ├── 查询该节点是否属于某个复合节点
              ├── 若属于且该复合节点正在运行
              │       └── 弹出确认对话框，提示冲突
              │           ├── 用户确认 → 停止复合节点 → 启动独立节点
              │           └── 用户取消 → 终止本次启动
              └── 否则 → 正常启动
```

```
场景 B: 用户启动复合节点
  start_selected_node_by_name()
      │
      └── check_composite_start(composite_name)
              │
              ├── 遍历复合节点内所有子节点
              ├── 检查是否有任何子节点正在独立运行
              │       └── 收集冲突子节点列表
              ├── 若有冲突
              │       └── 弹出确认对话框，列出冲突子节点
              │           ├── 用户确认 → stop_conflicting_subnodes() → 启动复合节点
              │           └── 用户取消 → 终止本次启动
              └── 否则 → 正常启动
```

**stop_conflicting_subnodes()** — 调用 `node_manager.stop_node()` 逐个子节点优雅停止，等待进程退出后返回。若停止超时或有节点停止失败，向上抛出警告但仍继续启动复合节点（复合节点启动后编排器会重新拉起子节点）。

**i18n 键位设计：**

| 键位 | 用途 |
|------|------|
| `_START_SUBNODE_CONFLICT` | 独立节点属于运行中复合节点时的冲突提示 |
| `_START_COMPOSITE_CONFLICT` | 复合节点包含独立运行子节点时的冲突提示 |

对话框提供三个选项：**确认停止并继续**、**取消**。取消是默认焦点，防止误操作。

### 2.2 资源监测双层架构

**Before：** 复合节点仅作为视觉分组标记，不参与资源监测。子节点与普通节点混在同一平级列表中，无法区分父子关系，也无法知道编排器进程的资源占用。

**After：** 复合节点拥有独立的监测行（展示编排器 PID + 资源占用），子节点以 `[sub]` 标签缩进展示在其下方。

```
▶ image_pipeline  PID=32604   12%  3.2GB  运行      ← 编排器进程（折叠/展开）
    inference [sub]             —     —     空闲      ← 编排器内部子节点（无独立 PID）
    preprocess [sub]            —     —     空闲
standalone_node                 5%   0.3GB  运行      ← 普通独立节点
    postprocess [sub]          85%   1.2GB  运行      ← 独立运行的子节点（有独立 PID）
```

**关键机制：**

1. **`get_composite_pid(comp_id)`** — 从 PID 文件 `__composite_{comp_id}.pid` 读取编排器进程的 PID。编排器启动时将 PID 写入此文件，停止时清理。

2. **`collect_group_stats(pid)`** — 获取一个进程及其所有子进程的聚合资源统计（CPU%、内存、状态）。编排器的主 PID + `psutil` 进程树遍历，自动包含所有子节点进程。

3. **`_format_memory(bytes)`** — 统一的内存格式化函数，根据数值大小自动选择 KB / MB / GB 单位，保持面板显示一致性。

4. **`_refresh_node_table()` 重写** — 渲染逻辑从单一平级列表变为二层结构：
   - 遍历 `node_manager.get_all_nodes()`
   - 若节点为复合节点且正在运行：创建父行（可折叠 `▶`/`▼`），查询 `collect_group_stats(pid)` 展示聚合数据
   - 遍历复合节点的子节点：创建缩进子行，标记 `[sub]`
     - 若复合节点在运行（inprocess 模式）：子节点无独立 PID，CPU/MEM 显示 `—`（已被聚合到父行）
     - 若子节点独立运行：显示独立 PID 及资源占用
   - 普通节点：与旧逻辑相同，作为独立行展示

5. **`_update_node_stats()` 重写** — 配合双层渲染结构，增量更新时识别父行 / 子行，分别刷新对应数据列。

## 三、行为变化

### 3.1 启动互斥防护

```
旧行为: 独立节点和复合节点可同时运行同一子节点，无任何警告
        → 两个进程争抢同一端口 / 同一输出文件 / 同一 GPU 资源

新行为:
  - 启动独立节点时: 检查是否属于运行中复合节点 → 有冲突则弹窗确认
  - 启动复合节点时: 检查是否有子节点独立运行 → 有冲突则弹窗确认
  - 用户取消 → 启动被阻止，已有运行进程不受影响
  - 用户确认 → 自动停止冲突方，继续启动
```

### 3.2 资源监测面板显示

```
旧行为:
  ┌────────────────────────────────────┐
  │ inference       15%  1.0GB  运行    │  ← 编排器内的子节点，但无法区分
  │ preprocess       8%  0.5GB  运行    │
  │ postprocess     85%  1.2GB  运行    │
  │ standalone       5%  0.3GB  运行    │
  └────────────────────────────────────┘
  问题: 看不到编排器进程; 无法区分父子关系; 无折叠能力

新行为:
  ┌────────────────────────────────────┐
  │ ▶ image_pipeline  PID=32604  12%  3.2GB 运行 │ ← 编排器行
  │     inference [sub]            —     —   空闲  │
  │     preprocess [sub]           —     —   空闲  │
  │ standalone                     5%  0.3GB 运行  │
  │     postprocess [sub]  PID=8801 85% 1.2GB 运行  │
  └────────────────────────────────────┘
```

### 3.3 父子进程依赖

```
编排器启动流程:
  1. 启动守卫检查 → 通过
  2. 启动编排器进程 → 写入 PID 文件
  3. 编排器内部启动子节点（inprocess）
  4. 资源监测面板通过 PID 文件找到编排器进程
  5. psutil 进程树遍历聚合子节点资源
  6. 面板展示双层结构

编排器停止流程:
  1. 调用 stop_node()
  2. 清理 PID 文件
  3. 资源监测面板检测进程消失 → 移除父行及所有子行
```
