# 状态机开发方案

## 〇、独立组件设计

**可以且应该作为独立组件开发。** 状态机模块不依赖任何 UI / 业务逻辑，可作为纯工具库独立开发、测试、集成。

### 组件结构

```
ui/core/state/              ← 独立组件包，零外部依赖（仅依赖 PySide6.QtCore.QObject）
├── __init__.py
├── base.py                 ← StateMachine 基类（纯逻辑）
├── node_runtime.py         ← 节点运行时状态机
├── composite_lifecycle.py  ← 复合节点生命周期状态机
├── canvas_mode.py          ← 画布交互模式状态机
├── edge_interaction.py     ← 边交互状态机
├── port_state.py           ← 端口连接状态机（二期）
├── config_sync.py          ← 配置同步状态机（二期）
└── tests/
    ├── test_base.py
    ├── test_node_runtime.py
    ├── test_composite_lifecycle.py
    ├── test_canvas_mode.py
    └── test_edge_interaction.py
```

### 独立开发优势

| 优势 | 说明 |
|------|------|
| **零耦合** | 不依赖画布、节点、配置等任何业务模块 |
| **可单测** | 每个状态机可完全脱离 UI 运行自动化测试 |
| **渐进集成** | 每写完一个，接入一个，不影响其他模块 |
| **类型安全** | 每个状态机自己的 enum 不与其他模块冲突 |
| **可替换** | 未来如果换 UI 框架，状态机层无需改动 |

## 一、Phase 0：基类 + 测试基础设施

### 目标

交付 `StateMachine` 基类及其完整单元测试，作为所有后续状态机的基础。

### 基类 API

```python
class StateMachine(QObject):
    state_changed = Signal(str, str)  # (old_state, new_state)

    def __init__(self, initial_state: str, transitions: list[Transition])
    
    @property
    def state(self) -> str: ...

    def handle(self, event: str) -> bool:     # 触发事件，返回是否成功
    def can(self, event: str) -> bool:        # 查询事件是否可触发（不执行）
    def reset(self) -> None:                   # 重置到初始状态
    def get_allowed_events(self) -> list[str]: # 当前状态允许的事件列表
```

### Transition 定义

```python
@dataclass(frozen=True)
class Transition:
    event: str
    source: str        # "*" = 任意状态
    target: str
    guard: Optional[Callable[[], bool]] = None   # 前置条件
    action: Optional[Callable[[], None]] = None  # 转换时的副作用
```

### 测试方法

| 测试编号 | 测试内容 | 测试方式 |
|----------|---------|---------|
| T0.1 | 正常状态转换 a → b | `sm = StateMachine("a", [Transition("go", "a", "b")]); assert sm.handle("go"); assert sm.state == "b"` |
| T0.2 | 禁止的转换返回 False | `assert not sm.handle("invalid_event")` |
| T0.3 | guard 返回 False 阻止转换 | `Transition(..., guard=lambda: False)` → 无状态变化、无 action 执行 |
| T0.4 | action 在转换成功时执行 | `side_effect = []; Transiton(..., action=lambda: side_effect.append(1))` → `side_effect == [1]` |
| T0.5 | `"*"(任意源状态) 通配符` 可从任何状态触发 | 先进入 b，再触发 `("*", "reset")` → 回到 target |
| T0.6 | `can()` 查询不改变状态 | 连续调用两次 `can("go")` 返回相同结果，state 不变 |
| T0.7 | `reset()` 回到初始状态 | 多次 handle 后 reset → state 回到 initial |
| T0.8 | `state_changed` 信号正确发射 | QSignalSpy 捕获 → 参数为 (old, new) |
| T0.9 | `get_allowed_events()` | 初始状态返回含通配符的合法事件列表 |
| T0.10 | 并发安全：连续 100 次 handle | 循环触发 → 状态始终合法 |

## 二、Phase 1：节点运行时状态机

### 目标

统一 `node_process.py` / `node_control_service.py` / `node_startup_queue.py` 中 3 套矛盾的状态值。

### 状态定义

```
STOPPED → STARTING → RUNNING ⇄ IDLE
                           ↓ crash
                        CRASHED
  STARTING → CRASHED (timeout)
  RUNNING → STOPPING → STOPPED
  STOPPING → CRASHED (kill failed)
  STOPPING → STOPPED (ok)
  CRASHED → STARTING (retry / restart)
```

### 迁移策略：兼容层

不直接改动 `node_info["status"]`，而是添加 property 代理：

```python
# node_runtime.py
class NodeRuntimeState(str, Enum):
    STOPPED = "stopped"
    STARTING = "starting"
    RUNNING = "running"
    IDLE = "idle"
    STOPPING = "stopping"
    CRASHED = "crashed"

class NodeRuntimeSM(StateMachine):
    def __init__(self, node_name: str):
        super().__init__("stopped", [
            Transition("start", "*", "starting"),
            Transition("start_ok", "starting", "running"),
            Transition("start_fail", "starting", "crashed"),
            Transition("child_idle", "running", "idle"),
            Transition("child_resume", "idle", "running"),
            Transition("stop", "running", "stopping"),
            Transition("stop", "idle", "stopping"),
            Transition("stop_ok", "stopping", "stopped"),
            Transition("stop_fail", "stopping", "crashed"),
            Transition("crash", "running", "crashed"),
            Transition("crash", "idle", "crashed"),
            Transition("retry", "crashed", "starting"),
            Transition("direct_stop", "crashed", "stopped"),  # 手动强制关闭
        ])

# 兼容层 - 添加到现有代码中
# node_info 的 status 读写 → 转发到状态机
```

### 改造点

| 文件 | 改动 | 风险 |
|------|------|------|
| `node_process.py` | `status = NodeRuntimeSM(node_name)` 替代 `node_info["status"] = "..."` | 中：需保留 `node_info["status"]` 读取兼容 |
| `node_control_service.py` | 替换 `NodeStatus` enum 的使用 | 低：`NodeStatus` 本就是 enum |
| `node_startup_queue.py` | `QUEUED/BLOCKED` 保留，`STARTING` 转发到状态机 | 低：仅 startup 阶段 |

### 测试方法

| 测试编号 | 测试内容 | 测试方式 | 预期结果 |
|----------|---------|---------|---------|
| T1.1 | 正常启动流程 | `STOPPED → handle("start") → STARTING → handle("start_ok") → RUNNING` | state = RUNNING |
| T1.2 | 启动失败 | `STOPPED → handle("start") → STARTING → handle("start_fail") → CRASHED` | state = CRASHED |
| T1.3 | 运行中 crash | `RUNNING → handle("crash") → CRASHED` | state = CRASHED |
| T1.4 | child idle 转换 | `RUNNING → handle("child_idle") → IDLE → handle("child_resume") → RUNNING` | 两个方向都 work |
| T1.5 | 正常停止 | `RUNNING → handle("stop") → STOPPING → handle("stop_ok") → STOPPED` | state = STOPPED |
| T1.6 | 停止失败 (强制终止) | `STOPPING → handle("stop_fail") → CRASHED` | state = CRASHED |
| T1.7 | crash 后重试 | `CRASHED → handle("retry") → STARTING` | state = STARTING |
| T1.8 | crash 后手动关停 | `CRASHED → handle("direct_stop") → STOPPED` | state = STOPPED |
| T1.9 | 不能从 STOPPED 直接到 RUNNING | `STOPPED → handle("start_ok")` | 返回 False，状态不变 |
| T1.10 | 不能从 RUNNING 再 start | `RUNNING → handle("start")` | 返回 False，状态不变 |
| T1.11 | state_changed 信号 emit | 每个转换是否 emit 正确 old/new | QSignalSpy count 正确 |
| T1.12 | 兼容层：`node_info["status"]` 读取仍可用 | 写旧代码 `node_info["status"]` → 读取结果 = state 值 | 值匹配 |
| T1.13 | 快速连续 start/stop 不产生非法状态 | `stopped → start → start(重复) → stop → stop_ok` | 重复 start 被拒绝 |

## 三、Phase 2：复合节点生命周期状态机

### 目标

消除 TOCTOU 竞态、资源泄漏、stop 无反馈。

### 状态定义

```
CREATED → STARTING → RUNNING
              ↓ timeout/err      ↓ crash
           CRASHED ←─────────────┘
   CREATED → REMOVING → REMOVED (decompress)
   STARTING → REMOVING → REMOVED (decompress during start)
   RUNNING → STOPPING → STOPPED → STARTING (restart)
   STOPPING → CRASHED (kill failed)
   CRASHED → STARTING (restart)
```

### 附属数据

```python
class CompositeLifecycleSM(StateMachine):
    def __init__(self, comp_id: str):
        self.comp_id = comp_id
        self.process: Optional[subprocess.Popen] = None  # 当前进程
        self.log_handles: tuple = (None, None)             # (stdout, stderr)
        self.pid: Optional[int] = None                     # 进程 PID
        # ... 状态定义
```

状态变化时，`action` 回调负责管理这些附属数据的生命周期（创建 Popen → 注册 `self.process` → 写 PID → 运行 → 关闭文件句柄 → 清除 PID → 重置）。

### 测试方法

| 测试编号 | 测试内容 | 测试方式 | 预期结果 |
|----------|---------|---------|---------|
| T2.1 | 正常生命周期 | `CREATED→start→STARTING→start_ok→RUNNING→stop→STOPPING→stop_ok→STOPPED` | 全程无异常 |
| T2.2 | 启动超时 → CRASHED | `STARTING → handle("start_timeout") → CRASHED`，检查 `process` 是否已 kill | state=CRASHED, process 被 terminate |
| T2.3 | 运行时 crash | `RUNNING → handle("crash") → CRASHED`，检查 `log_handles` 是否关闭 | state=CRASHED, handles 已 close |
| T2.4 | 停止失败 → CRASHED | `STOPPING → handle("stop_fail") → CRASHED`，检查清理逻辑 | state=CRASHED |
| T2.5 | TOCTOU 防护：重复 start | 线程 A: `start → start_ok → RUNNING`；线程 B: `start` (同时) | B 的 start 被拒绝（state 已不是 CREATED/STOPPED） |
| T2.6 | TOCTOU 防护：同时 stop | `RUNNING → stop` 两路并发 → 只执行一次 STOPPING | 第二次 stop 被拒 |
| T2.7 | CRASHED 后 restart | `CRASHED → handle("restart") → STARTING` | state 回到 STARTING |
| T2.8 | decompress 强制 stop | `RUNNING → handle("decompress")` → 内部自动触发 stop → STOPPING → STOPPED → REMOVING → REMOVED | 最终 REMOVED |
| T2.9 | decompress 时正处于 STARTING | `STARTING → handle("decompress")` → 内部 kill Popen → STOPPED → REMOVED | 进程被清理 |
| T2.10 | 异常路径资源清理 | 模拟 action 中抛异常 → 检查 `process` 和 `log_handles` 是否被 finally 清理 | 资源不残留 |

### 集成测试（需画布）

| 测试编号 | 测试内容 | 测试方式 | 预期结果 |
|----------|---------|---------|---------|
| T2.I1 | 创建复合 → 启动 → 停止 → 重启 → 停止 | 画布操作 | 每次都正确，日志连续不中断 |
| T2.I2 | 连续快速点"启动"按钮 5 次 | 模拟快速点击 | 只启动 1 个进程 |
| T2.I3 | 运行中直接点"解压缩" | 画布右键 → 解压缩 | 先 stop 再解压，无残留进程 |
| T2.I4 | stop 后立即 start（秒级间隔） | 按钮操作 | 新旧 processed 标记被清除，DAG 重新执行 |
| T2.I5 | 启动 → 手动 kill 进程 → 状态应转为 CRASHED | PowerShell `taskkill` 手动杀 Python 子进程 | state → CRASHED，UI 显示红色 |

## 四、Phase 3：画布交互模式状态机

### 目标

消除 pan/connect/box-select 模式冲突，新增 ESC 取消连线。

### 状态定义

```
NORMAL ──mousedown_anchor──▶ CONNECTING ──drop_on_input──▶ NORMAL
   │                            │ ESC / right click
   │                            ▼
   │                          NORMAL
   │
   ├──space+click──▶ PANNING ──mouse_release──▶ NORMAL
   │
   ├──alt+drag──▶ BOX_SELECTING ──mouse_release──▶ NORMAL
   │
   └──click_node──▶ SINGLE_SELECT ──click_empty──▶ NORMAL
```

**互斥保证：** 每次进入新模式前，`entry_action` 清除其他模式的视觉残留（rubber band / temp_edge / cursor）。

### 迁移策略

逐步替换 `canvas_view.py` 中的 bool 标志：

```python
# 旧代码
if self.canvas.is_connecting:
    ...
if self.canvas.is_pan_mode:
    ...
if self.canvas.is_box_selecting:
    ...

# 新代码
mode = self.canvas.mode_sm.state
if mode == CanvasMode.CONNECTING:
    ...
elif mode == CanvasMode.PANNING:
    ...
elif mode == CanvasMode.BOX_SELECTING:
    ...
```

   ├──press_handle──▶ HOLDING_HANDLE ──250ms──▶ DRAGGING_NEW_WP ──release──▶ IDLE
