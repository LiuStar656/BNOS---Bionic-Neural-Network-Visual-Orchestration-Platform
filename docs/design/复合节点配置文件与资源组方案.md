# 复合节点配置文件与资源组方案

## 概述

为每个复合节点创建独立的 `composite.json` 配置文件，使其拥有与独立节点 `config.json` 同等的身份标识能力。同时在资源监测系统中引入"资源组"概念，使复合节点及其子节点可被分组追踪。

---

## 一、问题分析

### 1.1 当前架构的 4 个缺陷

| 缺陷 | 现状 | 影响 |
|------|------|------|
| **无复合节点专属配置** | 所有复合节点信息混在 `node_clusters.json` 一个文件中 | 无版本管理粒度，无独立字段扩展空间 |
| **资源监测扁平化** | 每个节点独立一行，无分组关系 | `process` 模式下 5 个子节点看不出它们属于同一个复合节点 |
| **独立启动无归属** | 复合节点内子节点可单独 `start_node_process()`，资源面板只显示为独立节点 | 看不出来它"同时也是一个复合节点的内部节点" |
| **日志路径碎片化** | 日志写在 venv 目录内（`nodes/{display_name}_venv/logs/`），与复合节点身份分离 | 删除 venv 丢失日志；display_name 变更导致日志路径漂移；`node_list_ops` 查找路径不匹配 |

### 1.2 类比

```
独立节点:                                          复合节点 (当前):                    复合节点 (目标):
nodes/preprocess/                                node_clusters.json                   composite_nodes/c0f0d436/
├── config.json     ← 身份 + 配置                 (所有复合混在一起)                   ├── composite.json     ← 身份 + 配置
├── listener.py                                                                        ├── node_registry.json ← 子节点注册表
├── output.json                                                                        ├── logs/
└── .pid                                                                               │   ├── composite_output.log
                                                                                       │   └── composite_error.log
                                                                                       ├── orchestrator.py    ← 编排器
                                                                                       └── venv/              ← 合并 venv
```

### 1.3 日志路径对比

| 阶段 | stdout 路径 | stderr 路径 |
|------|------|------|
| **当前** | `nodes/{display_name}_venv/logs/composite_output.log` | `nodes/{display_name}_venv/logs/composite_error.log` |
| **当前 (无 display_name)** | `nodes/__comp__{id}_venv/logs/composite_output.log` | `nodes/__comp__{id}_venv/logs/composite_error.log` |
| **目标** | `composite_nodes/{comp_id}/logs/composite_output.log` | `composite_nodes/{comp_id}/logs/composite_error.log` |

**迁移收益**：
- 删除 venv 重建 → 日志不丢（venv 只放 Python 包）
- `display_name` 可随时改名 → 日志路径不变（依赖固定的 `comp_id`）
- `node_list_ops._get_log_files()` → 路径一致，不再错位

### 2.1 文件位置


### 2.3 字段说明

| 层级 | 字段 | 类型 | 说明 |
|------|------|------|------|
| 根 | `comp_id` | string | 唯一标识 |
| 根 | `display_name` | string | 用户可见名称 |
| 根 | `language` | string | 统一语言 |
| 根 | `version` | int | Schema 版本，升级兼容用 |
| runtime | `mode` | "inprocess"\|"process" | 运行模式 |
| runtime | `python_exe` | string\|null | 合并后 venv 路径 |
| nodes[] | `name` | string | 子节点名 |
| nodes[] | `path` | string | 相对项目根的路径 |
| nodes[] | `order` | int | 拓扑序号 |
| nodes[] | `entry` | string | 入口脚本 |
| nodes[] | `resource_limit` | object | **可覆盖独立节点的 resource_limit** |
| edges[] | `from/to/from_port/to_port` | — | DAG 边定义 |
| ports | `input/output` | list | 外部端口路由 |
| resource_group | `group_id` | string | 资源组 ID |
| resource_group | `composite_resource_limit` | object | **复合节点总资源预算** |
| orchestrator | `script_path/checksum` | — | 编排器信息 |
| canvas_meta | `position/original_positions` | — | 画布位置 |

## 三、node_registry.json 设计

### 3.1 文件位置

```
<project_root>/composite_nodes/<comp_id>/node_registry.json
```

### 3.2 Schema

```json
{
  "group_id": "grp_c0f0d436",
  "composite_name": "图片处理流水线",
  "comp_id": "c0f0d436",
  "registered_at": "2026-07-12T17:30:00",
  "nodes": {
    "preprocess": {
      "path": "nodes/preprocess",
      "status": "idle",
      "last_pid": null,
      "last_started": null,
      "independent_runs": 0
    },
    "inference": {
      "path": "nodes/inference",
      "status": "running",
      "last_pid": 47236,
      "launched_by": "user",
      "last_started": "2026-07-12T17:35:00",
      "independent_runs": 3
    },
    "postprocess": {
      "path": "nodes/postprocess",
      "status": "idle",
      "last_pid": null,
      "last_started": null,
      "independent_runs": 0
    }
  }
}
```

### 3.3 用途

`node_registry.json` 不是 BNOS 核心逻辑依赖的文件，而是**轻量级的状态记录簿**。它的作用是：

1. 记录子节点是否被**独立启动**（非通过编排器）
2. 记录最后的 PID + **启动来源**（`"user"` vs `"orchestrator"`）— 供启动守卫判断冲突
3. 当独立节点被拖入复合节点时，快速查找它属于哪个资源组

| 场景 | 如何使用 |
|------|---------|
| 用户在画布上右键 `inference` → Start（独立启动） | 更新 `inference.last_pid` / `status: "running"` / `independent_runs++` |
| 资源监测面板需要聚合资源组 | 读取所有 `last_pid` → `collect_process_resources(pids)` → 汇总行 |
| 用户在画布上启动整个复合节点（inprocess） | 不更新 registry（由 orchestrator 统一管理） |
| 用户在画布上启动整个复合节点（process） | 每个子节点独立启动，更新各自 `last_pid` |

```
│ ─────────────────────────────────────────────────────── │

```

### 4.2 SystemResourceCollector 新增方法

```python
# system_resource_collector.py

@staticmethod
def collect_group_stats(group_id: str, registry: dict) -> dict:
    """聚合资源组内所有活跃子节点的资源使用量。
    
    Args:
        group_id: 资源组 ID (如 "grp_c0f0d436")
        registry: node_registry.json 反序列化后的 dict
    
    Returns:
        {"total_cpu": float, "total_mem_mb": float, "active_count": int, 
         "per_node": {name: {"cpu": ..., "mem": ..., "pid": ...}}}
    """
    total_cpu = 0.0
    total_mem = 0.0
    active_count = 0
    per_node = {}
    
    for name, info in registry["nodes"].items():
        pid = info.get("last_pid")
        if pid and psutil.pid_exists(pid):
            cpu, mem = SystemResourceCollector.collect_process_resources(pid)
            per_node[name] = {"cpu": cpu, "mem_mb": mem, "pid": pid}
            total_cpu += cpu
            total_mem += mem
            active_count += 1
        else:
            per_node[name] = {"cpu": 0, "mem_mb": 0, "pid": None}
    
    return {
        "total_cpu": total_cpu,
        "total_mem_mb": total_mem,
        "active_count": active_count,
        "per_node": per_node,
    }
```

### 4.3 ResourceMonitor 面板新增行

`ResourceMonitor._update_table()` 中，对 `composite_node/` 目录下每个 `composite.json` 所属的资源组，追加汇总行：

```
汇总行样式：
- 可折叠（点击展开显示各子节点详情）
- 颜色与独立节点区分（如浅蓝色背景）
- 状态取所有子节点中最严重的（running/idle/error）
```

### 5.1 场景

用户在画布上右键 `inference` 节点 → Start（独立启动），此时 `inference` 是复合节点 `c0f0d436` 的内部节点。

### 5.2 追踪流程

```
用户右键 inference → Start
  │
  ├─ 1. start_node_process("inference")     ← 现有逻辑，不变
  │     → Popen, PID=47236

  ├─ 2. 新增：查找归属
  │     → 扫描 composite_nodes/*/composite.json
```

```
节点进程退出时（node_status_changed → stopped）:
  │
  ├─ 1. 现有逻辑，不变
```

## 七、复合节点生命周期

### 7.1 生命周期三阶段

```
创建（压缩）              运行时                    销毁（解压缩）
──────→                  ──────→                  ──────→

mkdir composite_nodes/   logs 写入                日志 → .archive/ 存档
写 composite.json        子节点注册表更新          rm -rf composite_nodes/<id>/
写 node_registry.json    venv 激活                 rm node_clusters.json 条目
mkdir logs/              资源组汇报                解除 NodeGroupManager
合并 venv                                         恢复独立节点到画布
```

### 7.2 解压缩时的清理规则

| 类型 | 操作 | 原因 |
|------|------|------|
| `composite_nodes/<id>/logs/` | **存档后删除** | 下次创建的复合节点不是同一个，旧日志会误导。但可能有诊断价值，先存档 |
| `composite_nodes/<id>/venv/` | **直接删除** | 合并 venv 是为这个复合节点定制的，解压缩后无用 |
| `composite_nodes/<id>/composite.json` | **直接删除** | 复合节点已不存在 |
| `composite_nodes/<id>/node_registry.json` | **直接删除** | 注册表随复合节点一起消亡 |
| `composite_nodes/<id>/orchestrator.py` | **直接删除** | 编排器随复合节点一起消亡 |
| `node_clusters.json` 条目 | **删除此条** | 复合节点已解压缩 |
| 独立节点的 `config.json` / `output.json` | **不动** | 这些属于独立节点，不是复合节点 |

### 7.3 日志存档目录

```
composite_nodes/
├── .archive/
│   ├── c0f0d436_a1b2c3d4_2026-07-12T17-35-00/
│   │   ├── composite.json        ← 存档时的快照，用于比对结构
│   │   ├── composite_output.log
│   │   └── composite_error.log
│   └── c0f0d436_e5f6a7b8_2026-07-12T19-10-00/
│       └── ...
├── c0f0d436/           ← 当前活跃的复合节点
│   └── ...
```

存档命名：`<comp_id>_<结构指纹>_<解压时间戳>/`

其中 `结构指纹` = SHA256(`nodes[]` + `edges[]`) 前 8 位 hex。作用：

| 场景 | 效果 |
|------|------|
| 同一复合节点多次解压 → 再压缩（结构不变） | 同一结构指纹，可区分"第几次解压" |
| 同一 `comp_id`，解压后删掉一个子节点 → 再压缩 | 不同结构指纹，**明确是不同代的复合节点** |
| 快速查看某次存档代表什么 | 读存档内的 `composite.json` 快照即可 |

### 7.4 清理伪代码

```python
# composite_node.py

def _decompress_and_cleanup(self, comp_id: str):
    """解压缩复合节点并清理所有产物。"""
    comp_dir = Path(f"composite_nodes/{comp_id}")
    
    # 1. 存档日志
    log_dir = comp_dir / "logs"
    if log_dir.exists() and any(log_dir.iterdir()):
        ts = datetime.datetime.now().strftime("%Y-%m-%dT%H-%M-%S")
        fingerprint = self._compute_structure_fingerprint(comp_id)
        archive_dir = Path(f"composite_nodes/.archive/{comp_id}_{fingerprint}_{ts}")
        archive_dir.mkdir(parents=True, exist_ok=True)
        # 同时存档 composite.json 快照，方便事后查看结构
        cfg_src = comp_dir / "composite.json"
        if cfg_src.exists():
            shutil.copy2(cfg_src, archive_dir / "composite.json")
        for log_file in log_dir.glob("*.log"):
            shutil.copy2(log_file, archive_dir / log_file.name)
        self._prune_archives(comp_id, max_count=10)
    
    # 2. 删除整个复合节点目录
    shutil.rmtree(comp_dir, ignore_errors=True)
    
    # 3. 从 node_clusters.json 中移除此条目
    ...
    
    # 4. 恢复独立节点到画布
    ...

def _prune_archives(self, comp_id: str, max_count: int = 10):
    """超出最大数量的旧存档自动删除。"""
    archive_base = Path("composite_nodes/.archive")
    archives = sorted(archive_base.glob(f"{comp_id}_*"), key=os.path.getmtime, reverse=True)
    for old in archives[max_count:]:
        shutil.rmtree(old, ignore_errors=True)

def _compute_structure_fingerprint(self, comp_id: str) -> str:
    """对复合节点的 nodes[] + edges[] 做 SHA256 前 8 位。
    
    相同结构 → 相同指纹；结构变化 → 指纹不同。
    """
    cfg = self._composites[comp_id]
    payload = json.dumps({
        "nodes": sorted(cfg["nodes"]),
        "edges": sorted((e["from"], e["to"]) for e in cfg.get("edges", [])),
    }, sort_keys=True)
    return hashlib.sha256(payload.encode()).hexdigest()[:8]
```

## 八、启动守卫：复合节点 ⇄ 子节点互斥

### 8.1 核心原则

**一个子节点同时只能有一个运行实例。** 它要么作为复合节点编排器的一部分运行，要么独立运行，不能两者同时存在。

```
正确状态:
  [复合节点运行]  ← orchestrator PID=100
    ├── preprocess  (in orchestrator 进程内)
    ├── inference   (in orchestrator 进程内)
    └── postprocess (in orchestrator 进程内)

  [独立运行]  ← 复合节点未启动
    preprocess  PID=200 (独立 python listener.py)
    inference   PID=300 (独立 python listener.py)

错误状态（需守卫拦截）:
  [复合节点运行]  ← orchestrator PID=100
    ├── preprocess  (in orchestrator)
    ├── inference   (in orchestrator)  ← 同时被复合节点占用
    └── inference   PID=300 (独立)     ← 同时独立运行 ← 冲突！
```

### 8.2 两层监控范畴

资源监测面板需明确区分两个层级：

```
┌────────────────────────────────────────────────────────────┐
│ ResourceMonitor Panel                                       │
├────────────────────────────────────────────────────────────┤
│ 复合节点层 (composite scope) — orchestrator 进程聚合         │
│ ▶ image_pipeline  │ 102% │ 3.6GB │ 100 │ ● running         │
│   (3 nodes inprocess)                                       │
│                                                             │
│ 独立节点层 (node scope) — 各自独立进程                        │
│   standalone_A     │  15% │ 0.5GB │ 501 │ ● running         │
│                                                             │
│ 独立运行子节点 (独立于复合节点之外)                            │
│   preprocess [grp] │  12% │ 0.3GB │ 200 │ ● running         │
│                                                             │
│ 已停止                                               │
│   inference  [grp] │   —  │   —   │  —  │ ○ stopped         │
└────────────────────────────────────────────────────────────┘
```

`[grp]` 标记表示该节点属于某个复合节点组，但当前以独立模式运行。当复合节点启动时，该行自动消失（因为节点已被编排器接管）。

### 8.3 启动独立节点时的守卫

用户右键 `inference` → Start：


### 8.4 启动复合节点时的守卫

用户右键 `image_pipeline` → Start：

```
┌─ 守卫 1: 查子节点独立运行状态
│    读取 composite_nodes/c0f0d436/node_registry.json
│    → 遍历所有 sub-nodes，检查 last_pid 是否存活
│    → psutil.pid_exists(pid)
│
├─ 守卫 2: 发现冲突
│    found = [("inference", 300), ("preprocess", 200)]
│    → 如果 found 非空:
│       弹出警告: "以下子节点正在独立运行:
│                  - inference   (PID=300)
│                  - preprocess  (PID=200)
│                  启动复合节点将先停止这些独立进程。
│                  [取消]  [停止并启动复合节点]"
│
├─ 守卫 3: 清理
│    如果用户确认:
│      for name, pid in found:
│        kill_process(pid)           ← 停止独立进程
│        更新 node_registry.json: status = "idle", last_pid = null
│
└─ 守卫 4: 启动复合节点
      start_inprocess(comp_id)  ← 现有逻辑
      → 资源面板隐藏独立子节点行，显示复合节点汇总行
```

### 8.5 资源面板的联动行为

| 事件 | 独立子节点行 | 复合节点汇总行 |
|------|:---:|:---:|
| 复合节点启动（inprocess） | 隐藏所有子节点的独立行 | 显示，包含所有子节点资源 |
| 复合节点停止 | 恢复之前的独立行状态 | 隐藏，释放资源 |
| 某子节点独立启动（复合节点未运行） | 显示，`[grp]` 标记 | 隐藏 |
| 某子节点独立停止 | 隐藏该行 | — |
| 复合节点解压缩 | 所有子节点变为普通独立节点，`[grp]` 移除 | 删除 |

```python
def guarded_start_node(node_name: str, nodes_data: dict):
    """启动节点前检查复合节点互斥。"""
    
    # 1. 查归属
    owner = _find_owning_composite(node_name)
    
    if owner:
        # 2. 查复合节点是否运行中
        if _is_composite_running(owner):
            # 3. 弹出警告，询问用户
            choice = themed_message(
                t(TK._START_SUBNODE_CONFLICT).format(
                    node=node_name, composite=owner["display_name"]
                ),
                buttons=["cancel", "stop_composite_and_start", "force"],
            )
            if choice == "cancel":
                return False
            elif choice == "stop_composite_and_start":
                stop_composite(owner["comp_id"])
            # force: 直接放行
        _update_registry(owner["comp_id"], node_name, "running")
    
    return start_node_process(node_name, nodes_data)


# composite_node.py

def guarded_start_composite(comp_id: str):
    """启动复合节点前检查子节点互斥。"""
    
    # 1. 查子节点独立运行状态
    registry = _load_registry(comp_id)
    conflicts = []
    for name, info in registry["nodes"].items():
        pid = info.get("last_pid")
        if pid and psutil.pid_exists(pid):
            conflicts.append((name, pid))
    
    if conflicts:
        # 2. 弹出警告
        details = "\n".join(f"  - {n} (PID={p})" for n, p in conflicts)
        choice = themed_message(
            t(TK._START_COMPOSITE_CONFLICT).format(
                composite=comp_id, details=details
            ),
            buttons=["cancel", "stop_and_start"],
        )
        if choice == "cancel":
            return False
        # 停止所有独立进程
        for name, pid in conflicts:
            kill_process(pid)
            _update_registry(comp_id, name, "idle")
    
    return start_inprocess(comp_id)
```

```
node_clusters.json          composite.json
```

保存时，`composite.json` 中的 `nodes`/`edges`/`ports`/`canvas_meta` 也会同步回 `node_clusters.json`（避免分叉）。

## 十二、遗漏与补全

### 12.1 复合节点嵌套

**场景**：用户将复合节点 A（含 3 个子节点）作为子节点拖入更大的复合节点 B。

**问题**：当前 `compress()` 只检查"无重叠复合节点"（两个复合不能有交集），但未禁止或支持"复合节点作为另一个复合的子节点"。`composite.json` 的 `nodes[].path` 假设指向 `nodes/xxx/`，嵌套时需指向另一个 `composite_nodes/<id>/`。

**决策**：第一版**禁止嵌套**。`compress()` 增加守卫：选中的节点中若包含已注册的复合节点 → 拒绝 + 提示"暂不支持复合节点嵌套，请先解压缩"。

---

### 12.2 process 模式下的守卫语义差异

**场景**：复合节点以 `process` 模式运行，编排器为每个子节点启动独立进程。

**问题**：8.4 的守卫在 `process` 模式下逻辑不同：
- `process` 模式：子节点进程由编排器启动，是合法的独立 PID
- 用户独立启动：也是独立 PID
- 两者外观相同，但从 `node_registry.json` 角度看，都记录了 `last_pid`

**补全**：`node_registry.json` 增加 `launched_by` 字段区分：

```json
"inference": {
  "status": "running",
  "last_pid": 47236,
  "launched_by": "orchestrator",   // "orchestrator" | "user" | null
  "independent_runs": 3
}
```

守卫逻辑调整：
- `launched_by == "orchestrator"` → 这是合法的复合节点子进程，不是冲突
- `launched_by == "user"` → 这是用户独立启动的，与复合节点冲突

---

### 12.3 node_registry.json 脏状态

**场景**：`start_inprocess()` 先更新 `node_registry.json` 为 `"running"`，然后 `subprocess.Popen` 失败。

**问题**：注册表显示 `"running"` 但进程不存在。下次守卫检查时 `pid_exists` 返回 False，误判为"未运行"从而允许重复启动。

**补全**：状态更新必须在 Popen 成功后进行。失败时回滚：

```python
try:
    proc = subprocess.Popen(...)
    _update_registry(comp_id, node_name, "running", pid=proc.pid, launched_by="orchestrator")
except OSError:
    _update_registry(comp_id, node_name, "idle", pid=None, launched_by=None)
    raise
```

---

### 12.4 子节点被外部删除

**场景**：用户在文件管理器中删除 `nodes/inference/` 目录，但 `composite.json` 仍注册它。

**问题**：启动复合节点时 `nodes[].path` 指向不存在的目录，编排器 import 失败。

**补全**：BNOS 启动时和 `start_inprocess()` 前增加路径校验：

```python
def _validate_composite_integrity(comp_id: str) -> list[str]:
    """返回缺失的子节点列表。"""
    cfg = load_composite_config(comp_id)
    missing = []
    for n in cfg["nodes"]:
        if not Path(n["path"]).exists():
            missing.append(n["name"])
    return missing
```

发现缺失 → 在画布上标记复合节点为"已损坏"状态，双击展开时提示"以下节点已丢失: inference"。

---

### 12.5 composite.json 损坏

**场景**：磁盘错误、手动编辑失误、JSON 格式错误。

**补全**：加载时三层防护：
1. `json.loads()` → `ValueError` 捕获 + 从 `node_clusters.json` 重建
2. Schema 校验：`"nodes"` 和 `"comp_id"` 必填，缺失 → 重建
3. `version` 不兼容 → 走迁移逻辑或报错

```python
def load_composite_config(comp_id: str) -> dict | None:
    try:
        data = json.loads(Path(f"composite_nodes/{comp_id}/composite.json").read_text())
        if "nodes" not in data or "comp_id" not in data:
            raise ValueError("缺少必填字段")
        return data
    except (OSError, ValueError, json.JSONDecodeError):
        logger.warning("composite.json 损坏，从 node_clusters.json 重建 %s", comp_id)
        return _rebuild_from_clusters(comp_id)
```

### 12.6 撤销解压缩

**场景**：用户解压缩复合节点后发现误操作，想恢复。

**问题**：`.archive/` 有完整的 `composite.json` 快照和日志，但无内置恢复流程。

**补全**：`.archive/` 中存档的 `composite.json` 包含完整 DAG 结构，可供恢复。但第一版不做自动恢复（复杂度高，使用频率低）。改为：
- 解压缩弹窗增加二次确认："解压缩后可通过 .archive/ 目录查看历史日志，但无法一键恢复。是否继续？"
- P3 迭代可增加"从存档恢复"功能
